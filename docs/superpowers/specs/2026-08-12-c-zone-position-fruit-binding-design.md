# C 区位置与水果绑定设计

## 目标

修复 C 区最短路线重排后，K230仍按二维码原始顺序判断水果而造成的“实际位置与指定水果错位”问题。

STM32继续负责地图、最短路线和实际访问顺序；K230把二维码中的水果与位置按相同索引绑定。STM32每次请求 C 区视觉处理时携带当前真实位置编号，K230按该位置查询指定水果，只判断画面中面积最大的有效检测框。

## 根因

二维码中的第 `i` 个水果与第 `i` 个位置是一一对应关系。例如：

```text
番茄
洋葱
南瓜
辣椒
番茄
洋葱
南瓜
辣椒
4,3,1,10,8,9,2,11
```

表示番茄对应位置 4、洋葱对应位置 3、南瓜对应位置 1、辣椒对应位置 10，其余项继续按相同索引对应。

当前 STM32只接收并重排位置，K230却用 `fruit_list[self.order]` 按二维码原始顺序递增，因此路线一旦改变，K230要求的水果就不再是机器人当前所在位置对应的水果。

## 方案与职责

采用“STM32发送当前物理位置，K230按位置查水果”的方案：

- STM32保留现有 C 区顺/逆方向最短路线规划；
- STM32每次转好云台后发送实际位置编号；
- K230只维护 `位置 → 指定水果` 映射，不复制 STM32路线算法；
- A、B 区没有二维码水果限制，继续使用普通 `send`。

不采用让 K230复制路线算法或让 K230下发完整任务序列的方案，避免两端地图、拐角和平局规则产生漂移。

## UART5任务协议

### STM32到K230

- A/B 区：`send\r\n`
- C 区位置 1：`send:1\r\n`
- C 区位置 10：`send:10\r\n`

直接扩展现有 `UpperCP_SendTask()` 白名单，不新增发送API。允许：

- `send`
- `send:1`～`send:12`
- `scan`
- `pour`

拒绝：

- `send:0`
- `send:13`
- `send:abc`
- `send:1xxx`
- 其他未知任务字符串

### K230到STM32

保留现有协议含义：

- `QR:<8个位置>;`
- `arm:0;`～`arm:6;`
- 语音协议保持现状

本次不修改 `arm` 指令编号含义。

## STM32位置保存

`AppWaypoint_t` 增加：

```c
uint8_t positive_position;  /* +90°视野对应的二维码位置，0表示无位置限制 */
uint8_t negative_position;  /* -90°视野对应的二维码位置，0表示无位置限制 */
```

所有 A/B 区航点及普通无动作航点的两个字段均为 0。现有航点初始化宏必须显式把新增字段初始化为 0，动态复用 `s_dynamic_route` 时也必须覆盖这两个字段，防止旧位置残留。

C 区规划映射：

- 位置 1～4：写入对应节点的 `positive_position`；
- 位置 5～8：写入对应节点的 `negative_position`；
- 位置 9～12：写入对应节点的 `positive_position`。

同一底盘停车点两侧都有目标时分别保存。例如位置 1 与位置 5 共用停车点：

```text
positive_position = 1
negative_position = 5
```

现有 `action_mask` 仍决定需要处理哪一侧，位置字段只负责告诉 K230当前侧对应哪个物理位置。

## STM32视觉请求

现有 `App_SendVisionTask()` 改为接收位置编号，并统一替换路线状态机中两处直接发送 `send` 的代码：

- 处理 `+90°` 第一视野时使用 `positive_position`；
- 处理 `-90°` 第二视野时使用 `negative_position`；
- 位置为 0 时调用 `UpperCP_SendTask("send")`；
- 位置在 1～12 时生成 `send:<位置>` 并调用同一个 `UpperCP_SendTask()`。

因此同一停车点可以依次产生：

```text
转到 +90° → send:1
转到 -90° → send:5
```

路线按顺时针或逆时针执行都不会影响水果对应关系。

## K230二维码映射

目标文件固定为：

`D:\codexproject\zhihuinongye\dayun\model\main.py`

K230保存：

```python
self.fruit_by_position = {}
self.current_position = None
self.current_target_fruit = None
self.enable_bad_fruit = False
```

二维码解析要求：

1. 水果数量与位置数量相同且恰好为 8；
2. 位置均为十进制 `1～12` 且互不重复；
3. 水果名均能转换为现有类别语音ID：番茄 15、辣椒 14、南瓜 13、洋葱 16；
4. 只有全部合法时才一次性覆盖 `fruit_by_position` 并发送现有 `QR:<位置>;`；
5. 无效二维码不部分更新映射、不发送 `QR`，继续扫描。

示例：

```python
fruit_by_position = {
    4: 15,
    3: 16,
    1: 13,
    10: 14,
    8: 15,
    9: 16,
    2: 13,
    11: 14,
}
```

不得使用当前默认水果/位置数组作为抓取兜底。STM32若扫码超时后按默认位置继续规划，而K230没有有效映射，则每个带位置请求均安全跳过。

## K230任务接收

- 收到普通 `send`：清空当前位置限制，按 A/B 区普通识别逻辑运行；
- 收到 `send:<1～12>`：查找 `fruit_by_position[position]`，存在时设置当前指定水果并进入识别；
- 收到带位置请求但数字越界、格式错误、映射为空或位置不存在：立即发送一次 `arm:5;` 并回到空闲；
- 普通未知字符串保持现有忽略策略。

二维码列表的 `order` 不再参与 C 区水果匹配，也不在处理完位置后递增。水果/位置列表如继续保留，仅用于屏幕显示，不能成为抓取判断依据。现有最后一项处理前提前清空列表的逻辑必须移除，避免边界错位。

## 最大框选择与识别规则

只处理面积最大的有效检测框：

- 从宽、高均大于 0 的有效框中选择面积最大者；
- 不再因为画面中存在 `bad` 类就让坏果抢占最大框；
- 较小框中的目标水果或坏果均忽略。

最大框稳定识别达到现有 50 帧阈值后，保持“先播报、后判断”顺序：

1. 播报实际识别到的水果类别；
2. 播报实际成熟度；
3. 再决定抓取或跳过。

处理规则：

- 最大框为坏果：当前 `enable_bad_fruit == False`，播报坏果后发送 `arm:5;`；保留独立坏果处理入口，未来启用时再接入实际坏果动作；
- 最大框为未成熟正常水果：播报后发送 `arm:5;`；
- C 区最大框水果类别与当前位置指定水果不一致：播报实际类别和成熟度后发送 `arm:5;`；
- C 区类别一致且成熟：进入现有视觉对准并最终发送 `arm:0;`；
- A/B 区普通 `send`：不做二维码类别匹配，最大框为成熟正常水果时进入现有对准抓取。

最大框不匹配时不寻找其他检测框，直接跳过整个当前位置。

## 状态清理与超时

所有跳过和完成分支统一清理：

- 当前标签与上一标签；
- 连续帧计数；
- 确认状态与坏果状态；
- 当前物理位置和指定水果；
- 任务状态回到空闲。

清理时机不得早于视觉对准/抓取指令完成，以免处理中途丢失当前请求上下文。

无检测结果时继续沿用现有 10 秒超时后发送 `arm:5;` 的策略。

## 验证标准

### STM32主机验证

- `UpperCP_SendTask()`接受 `send`、`send:1`、`send:12`、`scan`、`pour`；
- 拒绝越界、畸形和未知任务；
- C 区同一停车点两侧分别发送正确位置，例如 `send:1`、`send:5`；
- 顺/逆两种路线访问顺序下，每次请求都携带当前实际物理位置；
- A/B 区仍只发送普通 `send`；
- 动态路线复用后不存在旧位置字段残留。

### K230桌面逻辑验证

- 二维码水果与位置按相同索引建立映射；
- 数量不符、重复位置、越界位置、未知水果名不提交映射；
- 普通 `send`不启用二维码匹配；
- `send:<位置>`正确选择指定水果；
- 无映射、位置不存在或畸形位置请求立即产生一次 `arm:5;`；
- 最大框错误水果仍完成播报，但最终跳过；
- 较小框目标水果和较小坏果不影响最大框选择；
- 坏果开关关闭时跳过，并保留未来入口；
- 最后一项不会提前清空或错位。

### 硬件验证边界

- STM32源码完成后由用户使用 Keil编译目标工程并返回完整日志；
- K230桌面语法和逻辑测试不能证明 CanMV摄像头、KModel或UART硬件行为；
- 板端必须检查二维码解析、`send:<位置>`收发、实际播报、最大框选择、错误水果跳过和正确水果抓取。
