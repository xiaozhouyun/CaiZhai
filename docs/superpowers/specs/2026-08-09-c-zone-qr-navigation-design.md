# C 区二维码导航设计

## 目标

在进入 C 区导航前增加二维码扫描阶段。下位机发送 `scan\r\n`，接收并保存上位机返回的 8 个水果位置，根据位置分布选择较短的 C 区巡航方向，并只把云台转向实际存在水果的一侧。

## 已确认约束

- C 区入口航点为 `WAYPOINT(-2600.0f, 10.0f, PI, false)`。
- 默认水果位置为 `uint8_t fruits[8] = {4,3,1,10,8,9,2,11};`。
- 上位机返回格式为 `QR:4,3,1,10,8,9,2,11;`。
- 二维码数据恰好包含 8 个互不重复的位置，每个位置在 `1..12`。
- 二维码数组顺序不代表访问顺序，导航应按照位置分布选择较短路线。
- 扫码等待时间为 10 秒；超时后使用默认数组继续。
- 沿用当前工程的 C 区通道坐标和四层纵坐标，便于后续现场修改。

## 扫码状态与数据提交

A 区路线完成后先进入独立的 C 区扫码状态，不直接启动 C 区路线。进入该状态时停车并只发送一次 `scan\r\n`，随后等待有效 `QR:` 帧。

解析时先写入临时数组，只有同时满足以下条件才一次性覆盖全局 `fruits[8]`：

1. 恰好解析到 8 个十进制整数；
2. 每个数值在 `1..12`；
3. 8 个数值互不重复；
4. 帧中不存在多余字段或无法解析的字符。

无效帧不得部分覆盖默认值，并继续等待后续有效帧。收到有效帧后立即结束等待并规划路线；10 秒内没有收到有效帧时，保留默认数组并开始规划。

## 位置、导航点和云台方向

| 水果位置 | 底盘导航点 `(x,y)` mm | 云台角度 |
|---|---:|---:|
| 1 | `(-1900,1900)` | `+90°` |
| 2 | `(-1900,1400)` | `+90°` |
| 3 | `(-1900,900)` | `+90°` |
| 4 | `(-1900,400)` | `+90°` |
| 5 | `(-1900,1900)` | `-90°` |
| 6 | `(-1900,1400)` | `-90°` |
| 7 | `(-1900,900)` | `-90°` |
| 8 | `(-1900,400)` | `-90°` |
| 9 | `(-2600,1900)` | `+90°` |
| 10 | `(-2600,1400)` | `+90°` |
| 11 | `(-2600,900)` | `+90°` |
| 12 | `(-2600,400)` | `+90°` |

同一导航点最多停车一次。如果该点的 `+90°`、`-90°` 两侧都存在目标，停车后依次处理两侧；只有一侧存在目标时，不再转向或扫描另一侧。右侧通道的二维码位置只有 `9..12`，对应 `+90°`。

## 路线规划

保留现有 C 区矩形环路及拐角保护，不把同一坐标的左右水果重复建成底盘航点。规划过程先把 8 个水果位置转换为对应通道航点及云台方向位图，再从入口 `(-2600,10,PI)` 比较沿环路两个方向覆盖全部目标所需的路线长度，采用较短方向；长度相同时采用现有规划器的顺时针优先规则。

生成路线时：

- 目标停车点必须保留，并记录该点需要执行的云台方向；
- 同一坐标的两个目标合并到同一停车点；
- 必须保留转弯拐角，防止导航直接斜切；
- 直线上的非目标中间点可以省略；
- C 区完成后继续进入现有返回流程。

## 作业状态机

现有作业状态机仍负责升降、云台插补、发送 `send` 和等待抓取完成。每个动态航点增加方向信息：

- 只需 `+90°`：执行正向视野后进入下一航点；
- 只需 `-90°`：跳过正向视野，直接执行反向视野；
- 两侧都需要：先执行 `+90°`，完成后执行 `-90°`；
- 无作业：直接进入下一航点。

继续遵守现有机械安全顺序和非阻塞 Tick 结构，不引入任务内长时间阻塞等待。

## 验证标准

- `QR:4,3,1,10,8,9,2,11;` 能原样保存为 8 个位置。
- 少于或多于 8 项、越界、重复、非整数帧均不改变当前默认数组。
- 扫码状态发送一次 `scan\r\n`，有效帧到达后立即规划；无有效帧时满 10 秒使用默认数组。
- 位置映射与上表一致，同一点两侧目标只停车一次。
- 规划结果从 `(-2600,10,PI)` 出发，选择两种合法巡航方向中的较短路线并保留必要拐角。
- 单侧目标只执行对应云台角度，双侧目标依次执行两侧。
- 静态检查、协议解析检查通过；Keil 编译与实车路径、云台方向仍需用户在目标硬件上验证。
